# Подготовка к КР

## Когда я выберу rebase, а когда merge? Почему?

Rebase беру для своей ветки, пока её никто, кроме меня, не забрал. Перед тем как открыть PR, делаю git rebase main: мои коммиты встают поверх свежего main, история остаётся прямой, и ревьюеру не мешают merge-коммиты. Через rebase -i заодно склеиваю мелкие коммиты вроде «wip» и «fix typo».

Merge беру, когда ветку уже используют другие, и когда вливаю готовую ветку в main. Merge не переписывает существующие коммиты, а только добавляет коммит слияния, поэтому у коллег ничего не ломается.

## Что будет, если сделать rebase публичной ветки, с которой работают коллеги?

Rebase создаёт новые коммиты с новыми хешами, а старые выкидывает из ветки. У коллег в локальных копиях остаются старые коммиты. Чтобы отправить переписанную ветку, мне придётся делать push --force, и если кто-то успел запушить своё, его коммиты пропадут с сервера. А когда коллега сделает git pull, Git увидит две разошедшиеся истории и сольёт их. В ветке окажутся одни и те же изменения дважды, со старыми и новыми хешами, и разбираться в этом придётся вручную.

## Зачем нужен multi-remote и где он применяется?

Multi-remote позволяет одному локальному репозиторию работать с несколькими серверами. Где это встречается:

- Зеркало для бэкапа. Код лежит на GitHub и копией на GitLab или своём сервере. Если один сервис недоступен или заблокирован, работа не встаёт. На этой практике я так и настроил: git push origin отправляет сразу в devops-course-2026 и в devops-course-2026-mirror.
- Forking Workflow. origin указывает на мой форк, upstream на оригинальный репозиторий. Из upstream подтягиваю свежие изменения, в origin пушу свои ветки и оттуда открываю PR.
- Переезд с одного хостинга на другой. Добавляю новый remote, пушу туда все ветки и теги, а старый какое-то время держу параллельно.
- Деплой. Некоторые платформы, например Heroku и Dokku, принимают код через git push в свой remote.
